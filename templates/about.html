Acerca de este proyecto

PodWave — Documento de proyecto

{# ---------- 1. Problemática ---------- #}

🔍 1. Problemática

Los creadores de podcasts independientes necesitan un espacio simple para organizar y compartir sus episodios: las plataformas comerciales (Spotify, SoundCloud) exigen registros, priorizan contenido de grandes productoras y no permiten gestionar una biblioteca personal a medida. Por otra parte, una aplicación puramente de front end (como la versión original de PodWave en React) no puede persistir datos en el servidor, validar de forma confiable ni distinguir usuarios: todo vive en el navegador de cada visitante y se pierde al limpiar el almacenamiento local.

Se necesita un servicio de streaming de audio del lado del servidor, donde la biblioteca de pistas, las validaciones y la sesión de cada usuario se gestionen centralizadamente con Django.

{# ---------- 2. Objetivo general ---------- #}

🎯 2. Objetivo general

Desarrollar PodWave, una plataforma web de streaming de audio (podcasts) construida con Django 5.2.18 bajo el patrón MVT, que permita a cada usuario autenticado administrar una biblioteca de pistas (agregar, explorar, filtrar por género, editar y eliminar), armar listas de reproducción propias con su orden personal y reproducirlas desde un reproductor fijo que continúa sonando durante la navegación, evolucionando en tres etapas durante el semestre: interfaces y datos simulados (UA1), persistencia, sesiones y CRUD completo desde el sitio (UA2) y API REST (UA3).

{# ---------- 3. Usuarios y roles ---------- #}

👤 3. Usuarios y roles previstos

Rol Descripción Interacciones principales
Visitante (sin sesión) Cualquier persona que llega al sitio. Explora el inicio, la biblioteca y el detalle de pistas; reproduce audio; filtra por género; consulta las listas de reproducción públicas; se registra o inicia sesión.
Usuario registrado Oyente que crea una cuenta (ej. demo). Todo lo anterior + agregar pistas (subiendo un archivo o una URL) y armar sus listas de reproducción: editar y eliminar solo lo que él mismo creó (control por dueño).
Administrador Superusuario del sitio (ej. admin). Gestiona el catálogo completo (géneros, pistas y listas de todos los usuarios) desde Django Admin (/admin/).
{# ---------- 4. Alcance UA1 + proyección ---------- #}

🧭 4. Alcance de la primera etapa y proyección

La primera versión navegable se concentró en la configuración de Django, el flujo URL → View → Template, la cobertura de interfaces para los roles previstos y la navegación coherente, con datos de demostración definidos como estructuras de Python en podwave/datos_simulados.py (listas de diccionarios y tuplas) que llegan a las plantillas mediante el contexto de las vistas.

UA1 — Implementado

  • Proyecto Django 5.2 reproducible (venv + requirements).
  • Apps propias: podwave, pages, accounts.
  • URLs, Views y Templates con herencia de base.html.
  • Interfaces: inicio, biblioteca (con filtro por género), detalle, formulario, confirmación de borrado, login y registro.
  • Datos simulados con estructuras de Python + contexto.
  • Archivos estáticos organizados (CSS, JS, imágenes).

UA2 — Implementado (etapas 1 y 2)

  • Modelos Genre, Track, Playlist, PlaylistTrack + MySQL (migraciones con datos).
  • CRUD completo desde el sitio de pistas y listas (vistas genéricas), sin depender del Admin.
  • Gestión de pistas dentro de la lista: agregar, quitar y reordenar (N:M con orden).
  • Sesiones: login/logout/registro + control de acceso por dueño (404 a quien no lo es).
  • Formularios con validación de servidor y mensajes de confirmación/error (crispy + Bootstrap 5).
  • Django Admin + archivos de audio subidos (media files).

UA3 — Proyectado

  • API REST con Django REST Framework.
  • Serializers y endpoints JSON.
  • CRUD REST.
  • Autenticación por token/JWT.
  • Seguridad a nivel de API.

Fuera del alcance de esta entrega: reproducción con cola de pistas, marcadores de favoritos, búsqueda de texto completo, comentarios, estadísticas de escucha, carga por lotes y API pública — se incorporarán en etapas posteriores del mismo proyecto.

{# ---------- 5. Migración React -> Django ---------- #}

🚀 5. Migración Front End → Back End

Aspecto SPA original (React + Vite) Proyecto actual (Django 5.2)
Persistencia Local Storage (navegador) Base de datos MySQL + ORM (UA2) sobre datos simulados de UA1
CRUD Estado de React (useState/useEffect) Vistas genéricas: ListView, DetailView, CreateView, UpdateView, DeleteView
Validaciones validators.js (JavaScript) TrackForm + validaciones del servidor (forms.py)
Autenticación No tenía Login / Logout / Registro + sesiones (LoginRequiredMixin)
Plantillas Componentes JSX Lenguaje de plantillas Django (herencia de base.html)
Reproductor Player.jsx (componente persistente) player.js vanilla + sessionStorage (recuerdo de pista y minuto)
Administración No tenía Django Admin (/admin/)
{# ---------- 6. Arquitectura MVT ---------- #}

🤖 6. Arquitectura MVT

Django sigue el patrón Modelo · Vista · Plantilla (MVT), su versión del clásico MVC:

  • Modelo (podwave/models.py): define las tablas de la base de datos: Genre, Track, Playlist y PlaylistTrack (N:M con orden).
  • Vista (podwave/views.py): lógica de petición-respuesta y CRUD de pistas y listas.
  • Plantilla (templates/): HTML con herencia y etiquetas de plantilla.
  • URLs (urls.py): enrutamiento de cada vista a su ruta.
